# 現金回本點與雙變數敏感度矩陣 — 規格

> **狀態：規格草案，尚未實作。** 本文件記錄評估結論與實作範圍，程式碼另行開發。
> 計算引擎現況見 [`docs/architecture.md`](architecture.md) 第 4 節，資料結構見 [`docs/data-schema.md`](data-schema.md)。

要回答的兩個問題：

1. **這個車型專案幾年回本？** —— 逐年現金流與回本點。
2. **台數與匯率的變動，會把回本點推遲多久？** —— 雙變數敏感度矩陣。

---

## 1. 背景：現行模型是「單台 × LC 平均」

整套系統目前沒有時間維度。時間只在三個地方出現：

| 位置 | 用途 |
|---|---|
| `SalesMix.MonthlyVolume × 12 × LifeCycleYears`（`CalcEngine.gs:483`） | 開發總投攤提的分母 |
| `Scenarios.AmortMonthlyVolume × 12 × AmortLifeCycleYears`（`CalcEngine.gs:472`） | 攤提基準覆寫 |
| 前端 `basisFactor_`（`script.html:2016`） | **只是顯示換算**：單台 × 月銷量 × 12 |

第三項要特別留意：儀表板現有的「年度總額」**不是年度損益**，它是「單台金額 × 年台數」，
隱含假設每一年都一模一樣。

另外，`SalesMix` / `CostOfSales` / `DevInvestment` / `OperatingExpense` / `Parameters`
幾乎每張表都有 `EffectiveDate` 欄位，但**沒有任何一行計算讀它**
（`CalcEngine.gs` 裡零次出現，只有 `DataService.gs:757` 原樣回傳給畫面）。
系統早就替時間留了位子，只是從未啟用。

## 2. 前提

以下三點已確認，它們是本規格能大幅收斂的原因：

| # | 前提 | 消除了什麼 |
|---|---|---|
| 1 | **開發總投全部發生在 SOP 前**，目標低減也在 SOP 前達成 | 投資是 t=0 的一筆整數，不需要 `InvestYear`；低減率維持情境層級，不需要年度化 |
| 2 | **h1 固定營業費用 / h3 品牌廣宣 / h4 特別加發 是「單台標準值」**，不隨台數變動 | 不需要替科目加「固定/變動」屬性；除開發攤提外，所有科目都是與台數無關的單台常數 |
| 3 | **回本點採現金口徑** | 現金不看會計攤提怎麼分年，因此**完全不需要攤提排程**（`AmortStartYear` / `AmortYears` / 逐年攤提表一律不做） |

前提 2 的推論很重要：**台數對損益只剩一條影響路徑**

```
台數 → getLifeCycleUnits() → 開發攤提分母 → b5 / b8 / f3 / f4
```

## 3. 名詞與口徑

| 符號 | 意義 | 現行來源 |
|---|---|---|
| `I` | 低減後開發總投（元） | `amortizeDevInvestmentPerUnit_()` 的 `totalsByLine` 加總（`CalcEngine.gs:441`）；亦即 `getDevInvestmentSummary().targets[].Total` 的加總 |
| `N` | LIFE CYCLE 總台數 | `getLifeCycleUnits(scenarioId)`（`CalcEngine.gs:472`） |
| `K` | 單台營業淨利 | `lineValues.K` |
| `a` | 單台開發攤提 | `amortizeDevInvestmentPerUnit_()` 的 `perUnit` 加總，等於 `I / N` |
| `m` | **單台現金貢獻**（排除開發攤提） | `K + a` |
| `n*` | **損平台數** | `I / m` |

`perUnit` 加總而非只取 `b5 + b8 + f3 + f4`，是為了自動涵蓋使用者自訂的攤提落點
（`AutoSource = DEV_AMORT`，見 `applyDevAmortLines_`）。

### 現金口徑的定義

本規格的「現金」是**稅前、不含營運資金**的簡化口徑：

- 系統的 `K` 是營業淨利，**沒有企業所得稅**
- **沒有應收帳款 / 存貨的資金占用**
- 假設售出當期即為現金收付

拿去跟財務部的正式投資回收年比對時，差異就在這兩項。**這句話必須顯示在畫面上。**

## 4. 核心公式

### 4.1 損平台數

`K` 已經扣過單台開發攤提，把它加回去就是單台現金貢獻：

```
m  = K + a           其中 a = Σ perUnit = I / N
n* = I / m           ← 損平台數
```

### 4.2 一個好用的恆等式

把 `m = K + I/N` 代入：

```
n*     I                       N · I
──  = ─────────        n*  =  ─────────
N     N·K + I                 N·K + I
```

因此**帳面 `K` 的正負，決定 `n*` 落在 `N` 的哪一邊**：

| 帳面 `K` | 損平台數 | 判讀 |
|---|---|---|
| `K > 0` | `n* < N` | 以攤提基準衡量，帳面打平之前就回本，`1 − n*/N` 即安全邊際 |
| `K = 0` | `n* = N` | 剛好在第 `N` 台回本 |
| `K < 0` | `n* > N` | 以攤提基準衡量，帳面打不平 |

> **現有儀表板其實已經在回答「回不回得了本」了** —— `K` 的正負就是答案。
> 缺的只有「哪一年」，那需要年度台數曲線（第 5 節）。

### 4.3 `n*` 與攤提基準無關 —— 但上面那張表跟它有關

這一節是第 10 節「攤提基準覆寫保留」這個決定的直接後果，實作前務必讀懂。

`K` 已經扣掉 `a`，而 `m = K + a`，所以：

```
m = (每台其他收支 − a) + a = 每台其他收支
```

**`m` 與 `N` 無關，因此 `n* = I / m` 也與 `N` 無關。**
攤提基準怎麼設、有沒有用 `Scenarios` 的覆寫，都不會改變損平台數。
`N` 只影響帳面 `K` 怎麼分攤。

於是 4.2 那張表要加上限制條件：**表中的 `N` 是攤提基準**
（`getLifeCycleUnits()`，有覆寫就是覆寫值），不是實際銷售預估。
所以 `K > 0` 測的是「以攤提基準衡量帳面是否打平」，
**不是**「實際賣得夠不夠」。

真正的回本判定只有一條：

```
n*  ≤  Σ 年度台數        →  回得了本
```

兩者可能給出不同答案。`data-schema.md` 2.2 記載的 Gate F 案例正是如此：
銷售估 365 台/月，但開發投資以 300 台/月 × 12 年 = 43,200 台攤提。
攤提基準低於銷售預估時，單台攤提偏高、`K` 被低估，
**`K > 0` 是偏保守的判準 —— `K < 0` 仍然可能在現金上回本**，
因為實際賣得比攤提基準多。

畫面上兩個數字都要出現，並標明各自的分母，不要讓使用者誤以為它們該一致。

### 4.4 數值範例

`I` = 4.32 億、`N` = 43,200 台、`a` = 10,000 元／台：

| 單台 `K` | `m` | `n*` | `n*/N` | 判讀 |
|---|---|---|---|---|
| +5,000 | 15,000 | 28,800 台 | 0.67 | LC 內回本，安全邊際 33% |
| 0 | 10,000 | 43,200 台 | 1.00 | 剛好在 LC 最後一台回本 |
| −2,000 | 8,000 | 54,000 台 | 1.25 | LC 內回不了本 |

### 4.5 邊界情況

| 情況 | 處理 |
|---|---|
| `m ≤ 0` | 每賣一台現金反而流出，永遠不回本。顯示「不回本」而非 `∞` 或負數 |
| `I = 0` | 沒有開發投資，`n* = 0`。顯示「無開發投資」 |
| `N = 0` | 沿用 `amortizeDevInvestmentPerUnit_` 現有行為（回傳空攤提），`a = 0`、`m = K` |

### 4.6 損平台數只在「車型層級」有意義

`DevInvestment` 是**部門別層級、不綁車系**（見 `data-schema.md` 2.5），
所以 `I` 是整個車型共用的。`n*` 必須用**加權平均的 `m`** 去除，
算出來是「車型總台數」的損平點。

在單一車系欄位上顯示 `n*` 會誤導 —— 那等於假設「全部台數都是這個車系」。

**規則：`n*` 與回本年只顯示在加權平均欄位。** 單一車系欄位顯示「—」。

## 5. 資料模型改動

**只需要新增「年度台數曲線」一項。** 其餘資料表一律不動。

### 已定案：方案 B — 車型層級曲線

只存「該情境每一年的總台數」，各車系用現有 `SalesMixPct` 分攤。

| 欄位 | 型別 | 說明 |
|---|---|---|
| RowID (PK) | text | |
| ScenarioID (FK) | text | 情境即綁定車型，不需要另存 VehicleTypeID |
| Year | number | 相對年序，`1` = SOP 當年 |
| AnnualVolume | number | 該年總台數（車型層級） |

- 資料列數 = LC 年數（12 列／情境），輸入介面就是一列數字
- 限制：假設構成比逐年不變。需要各車系上市時間不同時再談車系層級

> 未採用的方案 A（車系層級 `SalesMixByYear`，`ScenarioID` + `VehicleID` + `Year`）
> 資料量是車系數 × LC 年數（5 × 12 = 60 列／情境），能表達各車系上市時間不同、
> 構成比逐年變化。目前沒有這個需求，不做。

### 一致性約束：跟「銷售構成」比，不是跟「攤提基準」比

`Σ AnnualVolume` 要對照的是 **`getSalesMixLifeCycleUnits(scenarioId)`**
（`CalcEngine.gs:483`，Σ 月銷量 × 12 × LC年限），因為兩者描述的是同一件事 —— 銷售預估。

**不要拿它去比 `getLifeCycleUnits()`。** 後者在有覆寫時是**攤提基準**，
與銷售預估本來就可以不同（見 4.3），比出落差再示警只會製造假警報。

兩者不一致時：

- **不要**自動改寫任一邊
- 比照現有 `weightedTotalCaveat_()` 的做法，在畫面上標出差幾台並說明怎麼調回來

## 8. 敏感度分析（單變數 / 雙變數，同一畫面）

### 8.1 三種模式

同一個子頁籤，頂部一列切換要讓幾個變數動。未選為變數的那一項固定在現況值，並顯示出來。

| 模式 | 變數 | 未選變數 | 呈現 |
|---|---|---|---|
| **A · 匯率敏感度** | 匯率（單一幣別） | 台數固定 = 現況 | 一維：小倍數折線 + 表格 |
| **B · 台數敏感度** | 台數縮放 | 匯率固定 = 現況 | 一維：小倍數折線 + 表格 |
| **C · 雙變數** | 台數 × 匯率 | — | 二維：色階矩陣 + 表格 |

**後端只有一個函式**（見 8.6）：單變數就是雙變數其中一軸只有一個值的特例。
前端三種模式共用同一份回傳結構，差別只在怎麼畫。

### 8.2 指標 × 變數有效性 —— 無效組合必須停用

**這是設計上最容易做錯的一點。** 不同指標之下，台數軸的意義完全不同：

| 指標 | 台數軸 | 匯率軸 | 說明 |
|---|---|---|---|
| 單台 `K` | 有效 | 有效 | 台數透過攤提稀釋影響 `K`，是 1/x 曲線 |
| **損平台數 `n*`** | **無效（整排相同）** | 有效 | `n* = I / m`，`I` 與 `m` 都不含台數 |
| **回本年** | **有效** | **有效** | 台數決定「多快賣到 `n*` 台」，不是「`n*` 是多少」 |

由此得到一條 UI 規則：

> **`n*` 只在「匯率」為唯一變數（模式 A）時可選。**
> 模式 B 與模式 C 的指標選單要把 `n*` **停用並附上原因**，
> 不能讓使用者選了之後才看到一排一模一樣的數字 —— 那看起來像功能壞掉，不像設計。

反過來，**模式 A（匯率單變數）三個指標全部可選**，這也是唯一能同時看懂
「匯率如何同時推高 `n*` 又推遲回本年」的視角。

### 8.3 軸的定義：用相對基準的偏移，不要用絕對值

兩軸都以「相對現況」定義，這樣跨情境、跨幣別都可比，使用者也容易講：

| 軸 | 定義 | 預設刻度 |
|---|---|---|
| 台數 | 縮放係數 `k`，**整體套在年度台數曲線上**（曲線形狀不變），`N` 同步縮放 | `0.7 / 0.8 / 0.9 / 1.0 / 1.1 / 1.2 / 1.3` |
| 匯率 | 選定幣別相對現況的百分比偏移 `Δ`，只作用於該幣別 | `−20% / −15% / −10% / 0 / +10% / +15% / +20%` |

軸標籤要**同時顯示相對值與絕對值**（例：`+10%　JPY 0.242`），
否則使用者無法跟「匯率設定」頁上的數字對起來。

> **基準格（`k = 1.0`、`Δ = 0`）必須等於現行儀表板算出的同一個數字。**
> 畫面上要標出這一格，它同時是使用者的定位點與實作的驗證點（見第 11 節）。

### 8.4 單變數模式：小倍數，絕不用雙 y 軸

單變數模式只有一軸，所以**可以同時看多個指標** —— 但
`n*`（台）、回本年（年）、單台 `K`（元）單位互不相同，
**不可以塞進同一張圖的兩個 y 軸**。

作法是**小倍數**：一個指標一張小圖，上下排列、共用同一條 x 軸，各自有自己的刻度。
這樣既能一眼看出三者的走勢是否同向，又不會用兩個 y 軸製造假的交叉點。

每張小圖：2px 線、端點加標記、基準點（`Δ = 0` 或 `k = 1.0`）用實心點標出並直接標值，
其餘點只在 hover 時顯示。下方附同一份資料的表格。

### 8.5 雙變數模式：色階規則

一格一個數字，只能一個指標。

- **色階是 sequential（單一色相、淺 → 深）**，不是彩虹、也不是紅綠對撞。
  回本年越晚 = 越深。
- **「LC 內不回本」是狀態，不是色階的延伸。** 這些格子用
  status 色（`--deficit` 鏽橙）加文字標示，並且**排除在色階的值域之外** ——
  否則一格無限大會把整個色階壓平，其餘格子全部看起來一樣。
- 每格直接印數字（矩陣格數少，不必靠 hover 才看得到值），hover 再補完整說明
  （該格的台數、匯率絕對值、`n*`、回本年、單台 `K`）。
- 基準格加一圈明顯的外框。

### 8.6 API

一個函式服務三種模式：

```js
function calculateSensitivity(scenarioId, spec) {
  // spec = {
  //   volumeAxis: [0.7, 0.85, 1.0, 1.15, 1.3],        // 年度台數曲線的縮放係數；[1.0] = 不動
  //   fxAxis:     { currency: 'JPY', deltas: [-0.2, -0.1, 0, 0.1, 0.2] },  // [0] = 不動
  //   metric:     'paybackYear' | 'breakEvenUnits' | 'K'
  // }
  // 回傳 {
  //   rowAxis: { kind:'volume', labels:[], values:[] },
  //   colAxis: { kind:'fx', currency:'JPY', labels:[], values:[], absolute:[] },
  //   cells:   [[{ value, withinLifeCycle, breakEvenUnits, paybackYear, K }]],
  //   baseCell:{ r, c },
  //   metric:  'paybackYear'
  // }
}
```

單變數模式就是其中一軸只傳一個值。前端依 `rowAxis.values.length`、
`colAxis.values.length` 決定畫小倍數還是矩陣，不需要第二支 API。

### 8.7 匯率的雙重影響

匯率同時影響兩條路徑，**方向相同**：

| 路徑 | 程式位置 | 效果 |
|---|---|---|
| 外幣開發投資換算 | `CalcEngine.gs:430` | 匯率升 → `I` 上升 |
| 外幣材料成本換算 | `CalcEngine.gs:153` | 匯率升 → `m` 下降 |

兩者都讓 `n*` 惡化，所以 `n*` 對匯率相當敏感 —— 這正是模式 A 的價值所在。

> **已定案：匯率軸一次只動一個幣別，搭配幣別選擇器；不提供「全部外幣同步 ±%」。**
> 理由是實務上的曝險集中在單一幣別（JPY 或 CNY），把所有幣別綁在一起同步變動
> 會把「哪一個幣別在痛」這個資訊抹掉。
>
> 選擇器的選項來自 `getConfiguredCurrencies(scenarioId)`（`DataService.gs:815`，
> 與「銷貨成本」頁的幣別選單同源），它回傳**本位幣 + 該情境設定過現況匯率的幣別**。
> 注意它會把本位幣放在陣列第一個 —— 敏感度的幣別選擇器**必須把本位幣濾掉**，
> 本位幣沒有匯率可調（`fxRateFor_` 對它一律回傳 1）。
> 預設選該情境外幣金額最大的幣別；濾掉本位幣後沒有任何幣別時，
> 模式 A 與模式 C 停用並說明原因（該情境沒有任何外幣曝險）。

### 8.8 必要的重構

`calculatePLCoreUncached_` 目前自己讀表（`getSalesMix` / `getParameters` /
`getCostOfSales` / `getOperatingExpense`）。敏感度需要「不存檔就試算」，
因此要把「讀表」與「算」分開：

```
loadPLInputs_(scenarioId, vehicleId)  →  inputs 物件
calcFromInputs_(inputs)               →  lineValues
```

這個模式在 codebase 已有先例：`amortizeDevInvestmentPerUnit_(scenarioId, overrideRows)`
與 `previewDevInvestmentSummary()`（`CalcEngine.gs:415, 550`），
開發總投頁面的即時預覽就是這樣做的。

### 8.9 實作陷阱

> **`PL_CORE_MEMO_` 必須繞過。**
> 它以「情境\|車系」為鍵（`CalcEngine.gs:93-97`），只有寫入時才會被
> `resetExecutionCaches_()`（`Utils.gs:66`）清掉。敏感度每一格的情境與車系都相同，
> 不繞過的話 **整張矩陣會全部拿到同一個數字** —— 而且看起來像「功能沒作用」，不像 bug。

### 8.10 效能

不是問題。雙變數 7×7 = 49 格、單變數 7 格，每格一次純 JS 運算；
讀表有 `SHEET_CACHE_` 單次執行快取（`Utils.gs:43`），
**Sheets API 呼叫次數不隨格數成長**。距離 Apps Script 的 6 分鐘上限很遠。
加權平均會再乘上車系數，仍在安全範圍。

## 9. 明確不做的事

列在這裡，避免範圍蔓延：

| 不做 | 原因 |
|---|---|
| 攤提排程（`AmortStartYear` / `AmortYears` / 逐年攤提） | 現金口徑不看會計攤提怎麼分年（前提 3） |
| 挑戰低減率年度化 | 低減在 SOP 前達成（前提 1） |
| 逐年成本／售價假設（材料降價曲線、年度調價） | 這是另一個層級的工程（三個矩陣頁面要從 2D 變 3D、`DataService` 全面改鍵）。回本點與趨勢不需要它 |
| 科目的「固定／變動」屬性 | h 類是單台標準值（前提 2） |
| NPV / IRR / 折現 | 需要折現率政策，且非本次要回答的問題 |
| 殘值 / 減損 | 投資在 SOP 前一次發生、現金口徑下不產生未攤提餘額的問題 |

## 10. 已定案的決策

規格階段的待確認事項已全部收斂，實作時不必回頭翻對話。

| # | 項目 | 決定 | 落在 |
|---|---|---|---|
| 1 | 年度台數的層級 | **車型層級**（方案 B）：一情境一條年度總台數曲線，各車系用 `SalesMixPct` 分攤 | 5 |
| 2 | 回本判定的台數依據 | **以該情境的年度台數為準**（`Σ AnnualVolume`），不是攤提基準 | 4.3 |
| 3 | `Scenarios` 的攤提基準覆寫 | **保留**。它與年度台數是兩個不同用途的數字，不是重複 | 4.3 |
| 4 | 匯率軸的範圍 | 一次只動一個幣別 + 幣別選擇器，不做全部外幣同步 | 8.3 / 8.7 |
| 5 | 單變數與雙變數的關係 | 同一畫面三種模式，後端一支 API，單變數是一軸長度 1 的特例 | 8.1 / 8.6 |
| 6 | `n*` 的可選性 | 只在匯率為唯一變數時可選，其餘模式停用並附原因 | 8.2 |

### 2 與 3 合起來的意思

這兩個決定不衝突，因為兩個台數服務不同目的：

| 數字 | 來源 | 用途 |
|---|---|---|
| **攤提基準 `N`** | `getLifeCycleUnits()`（有覆寫就用覆寫） | 算單台攤提 `a = I/N` → 影響帳面 `K` |
| **年度台數 `Σ AnnualVolume`** | 新的年度曲線 | 決定何時累計到 `n*` → 回本年 |

`n*` 本身與兩者都無關（`n* = I/m`，`m` 不含 `N`，見 4.3）。
所以保留覆寫不會污染回本分析，而回本分析也不需要動攤提基準 —— 各自獨立。

## 11. 驗證計畫

沿用 `tools/` 的記憶體模擬層，新增 `tools/verify-payback.js`：

| 測試 | 內容 |
|---|---|
| 恆等式 | `n* / N == I / (N·K + I)`，用 Gate F 實際數字驗（`N` = 攤提基準） |
| **攤提基準無關** | **改動 `Scenarios.AmortMonthlyVolume` / `AmortLifeCycleYears` 後，`n*` 必須完全不變**（`K` 會變）—— 這是 4.3 的核心結論，也是最容易寫錯的一條 |
| 邊界 | `K = 0` 時 `n* == N`；`m ≤ 0` 時回傳「不回本」而非負數／`Infinity` |
| 累計一致 | `Σ 年度現金流 == m × Σ AnnualVolume`；當 `Σ AnnualVolume == N` 時，累計現金收斂到 `N × K` |
| 回本判定 | 用 `n* ≤ Σ AnnualVolume` 判定，**不是**用 `K > 0`；兩者在覆寫生效時可能給出不同答案（驗 4.3） |
| 台數縮放 | 年度台數整體 ×k 時，`n*` **不變**、回本年提前（驗 8.2 那張表的結論） |
| 匯率單調 | 匯率上升時 `n*` 單調惡化（驗 8.7 的雙路徑同向） |
| 敏感度基準格 | 基準格（k=1.0、Δ=0）== 現行儀表板算出的同一個數字（防止重構走樣） |
| 單/雙變數一致 | 單變數結果 == 雙變數同一列／同一欄的切片（兩者共用同一支 API，不得有第二套算法） |
| 無效組合 | 模式 B／C 選 `n*` 時 API 應回報該組合無效，而不是回傳一排相同數字 |

另外，第 8.8 節的重構完成後，`tools/verify-gatef.js` 的 317 格逐格驗算**必須完全不變** ——
這是重構沒有改到計算結果的保證。
